## 01 — سكربت الإعداد الأول (Setup Wizard)

**ما هو:** أداة إنشاء مشروع بأمرٍ واحد — لا سكربت إعداد يُشغَّل يدوياً بعد
استنساخ عادي. البنية النهائية المتّفق عليها **جزءان منفصلان عمداً**:

1. **مُطلِق خارجي ثابت** (`app_template_cli`) — حزمة صغيرة تُفعَّل مرّة على
   الجهاز، ومهمّتها الوحيدة: استنساخ **أحدث نسخة** من مستودع القالب، ثم
   استدعاء الخطوة التالية تلقائياً. *(معلَّق — يحتاج قرار اسم/مكان مستودع
   GitHub جديد، ليس قراراً تقنياً)*.
2. **سكربت الحوار يعيش داخل القالب نفسه** (`scripts/setup_project.dart`) —
   ✅ **منجَز (2026-09-14)**. لأنه يُستنسَخ مع كل مشروع جديد، أي تحسين عليه
   يصل تلقائياً لأي مشروع **قادم** (لا الموجود) بلا أي عمل إضافي — هذا ما يحقق
   الشرط الذي طُرح بالنقاش: "التعديل على القالب ينعكس على المشروع الذي يليه".

**لماذا الآن:** الفحص الشامل (2026-09-13) وجد أن `applicationId` يبقى
`com.example.app_template` والتوقيع debug بالـrelease — فجوة موثَّقة كخطوة
يدوية، بالضبط ما ينساه فريقٌ يبني تحت ضغط وقت.

**تصنيف الأسئلة (القرار الجوهري بالنقاش)** — لا تُسأل كل الأعلام الـ٢٣:

| الفئة | تُسأل؟ | لماذا |
|---|---|---|
| الهوية (اسم، Application ID) | ✅ دائماً | لا رجعة سهلة فيها لاحقاً |
| وحدات بكلفة خارجية حقيقية (`accessControl`, `dataTransfer`, `offlineSync`, `multiDevice`, `inAppUpdates`, `crashReporting`, `analytics`, `remoteConfig`) | ✅ عبر نمط جاهز (بسيط/مؤسسي) أو فردياً (مخصّص) | تحتاج تنسيقاً مع الباك أو حساب Firebase — قرارٌ واعٍ لا نسياناً |
| كل شيء آخر (صلاحيات المنصّة، biometrics، clipboard، haptics...) | ❌ أبداً | بلا كلفة خارجية — تُفعَّل لحظة الحاجة الفعلية بالكود مباشرة |

**قاعدة صارمة يتّبعها السكربت:** لا يحذف كوداً ولا تبعيةً أبداً — يبدّل قيماً
فقط (أعلام + هوية). هذا يجعله بسيطاً تقنياً بلا حاجة لأداة قوالب معقّدة (بحثنا
Mason واستُبعدت لهذا السبب بالذات: قوّتها بالحذف/الإدراج الشرطي للملفات، ونحن
لا نريد أياً منهما).

**ما نُفِّذ فعلياً بـ`scripts/setup_project.dart`:**
- حوار: نمط جاهز → الهوية → الوحدات (إن "مخصّص").
- يكتب: `flavor_settings.json` (الهوية الحقيقية لكل flavor) ·
  `android/app/build.gradle.kts` (`namespace` + `applicationId` الافتراضي) ·
  `ios/Runner.xcodeproj/project.pbxproj` (`PRODUCT_BUNDLE_IDENTIFIER`، بما فيها
  هدف `RunnerTests`) · `ios/Runner/Info.plist` (`CFBundleDisplayName`/`Name`) ·
  وصف `pubspec.yaml` · أعلام `app_features.dart`.
- يُشغِّل `sync_flavors.dart` تلقائياً — الملفات المشتقّة (`strings.xml` لكل
  flavor، أيقونات، `launch.json`) تُعاد توليدها من `flavor_settings.json`
  الجديد بدل تحريرها يدوياً.
- يكتب `.template_manifest.json` (كل قرار + `git rev-parse --short HEAD` وقت
  الإنشاء) — يجيب لاحقاً "لماذا هذا العلَم بهذه القيمة؟" بلا حفر بالتاريخ.
- يطبع تذكيراً واحداً لكل خيار `نعم` له كلفة تجهيز خارجية.
- يُشغِّل تلقائياً `flutter pub get` → `dart analyze lib` → `flutter test` →
  `check_structure.dart` كفحص صحة نهائي، ويفشل صراحةً (`exit(1)`) إن فشل أيٌّ منها.
- ✅ **جُرِّب فعلياً** على نسخة معزولة من المستودع (استبدال هوية كامل + ٨ أعلام)
  والنتيجة نظيفة: `dart analyze` بلا مشاكل، وكل الملفات المتوقَّعة صحيحة.

**عمداً خارج النطاق** (قرار موثَّق بالتفصيل داخل السكربت نفسه، لا سهو):
- اسم حزمة Dart (`app_template`) — يمسّ كل `import` بـ`lib/`، وCLAUDE.md يصفه
  "مرّة واحدة أو أبداً". قرار بهذا الحجم يستحق مراجعة يدوية واعية.
- إعادة توليد لوحة الألوان الكاملة (`app_palette.dart`, +12 درجة) من لون علامة
  واحد — لا أداة بالقالب تُنتج تدرّجاً موثوقاً من قيمة واحدة اليوم، والتدرّج
  الحالي يدويّ مدروس. تبديل الألوان يبقى خطوة يدوية موثَّقة، متبوعةً بـ
  `flutter test test/color_contrast_test.dart`.

**قرار (2026-09-14): المُطلِق الخارجي `app_template_cli` مؤجَّل — لا مرفوض.**
المشروع مربوطٌ فعلياً بمستودع GitHub قائم وله اسمٌ ورفعٌ منتظم، فلا داعي
لمستودعٍ ثانٍ الآن. **البديل العامل اليوم بلا أي إعداد إضافي:**

```bash
git clone <رابط المستودع الحالي> my_app && cd my_app && dart run scripts/setup_project.dart
```

استنساخٌ عادي (أو زر GitHub "Use this template" لتاريخٍ نظيف) ثم أمرٌ واحد —
خطوتان بدل ثلاث، وبلا أي مستودع/حزمة يجب صيانتها. **يُعاد فتح المُطلِق
المستقل فقط لو صار الفرق (كلمة واحدة مقابل هاتين الخطوتين) يستحق العناء
فعلياً بمشروع مستقبلي** — لا قبل ذلك.

**وبهذا يُغلَق البند #01 بكامله**: الجزء الجوهري (`setup_project.dart`) منجَز
ومُختبَر، والجزء المؤجَّل قرارٌ واعٍ لا عملاً ناقصاً.

- تنسيق مع الباك (`backend_template`) بنفس الأمر — **استُبعد صراحةً** من هذا
  البند بقرار المستخدم (2026-09-14).
- `check-updates` — يعتمد على مُطلِقٍ مستقل غير موجود بعد، فمؤجَّل معه.

## 02 — مولّد الشرائح (Feature Scaffolding)

✅ **منجَز (2026-09-14)** — `scripts/scaffold_feature.dart`.

**ما هو:** `dart run scripts/scaffold_feature.dart <feature_name>` يولّد شريحة
CRUD كاملة بكل طبقاتها (dtos → models → datasources → repositories →
entities → params → usecases → cubits → pages) مطابقةً لما يصفه
[`lib/features/CLAUDE.md`](../lib/features/CLAUDE.md) §CRUD-PATTERNS و
[`lib/core/CLAUDE.md`](../lib/core/CLAUDE.md) §API-GENERATOR معاً — لا بنية
فارغة، بل ١٨ ملفاً **تُصرَّف وتعمل فوراً** بحقلٍ تجريبي واحد (`title`).

**لماذا الآن:** هذه البنية كانت تُنسَخ يدوياً لكل feature جديدة بكل مشروع
مستقبلي — نسخٌ يدويّ عرضة لنسيان طبقة أو تسمية خاطئة تخالف القاعدة الصارمة
(`SafeCubit` لا `Cubit`، `@freezed` إلزامي، `handle()` لا try/catch، إلخ).

**ما نُفِّذ فعلياً:**
- قوالب raw strings بـ`__tokens__` (لا استيفاء Dart مباشر) — تفادياً لتعارض
  `$` الحرفي المطلوب بأسطر مثل `@PUT('${ApiUrls.x}/{id}')` مع استيفاء سكربت
  التوليد نفسه.
- يصل تلقائياً: `api_urls.dart` (سطر جديد) · `injection_module.dart`
  (تسجيل ApiService) · `router.dart` (مساران) · `ar.json`/`en.json` (٥ مفاتيح،
  مُعاد ترتيبها أبجدياً بعد الإضافة).
- يشغّل `gen_code.dart` تلقائياً ثم فحص صحة كامل (`analyze` → `test` →
  `check_structure`) — يفشل صراحةً إن فشل أيٌّ منها.
- الودجات مقسَّمة بالفعل (`_FormBody` مستخرجة) امتثالاً لسقف `build()` ٥٠
  سطراً — أول تشغيل تجريبي كشف مخالفة F19 حقيقية (51 سطراً) صُحِّحت بالاستخراج.

**عثرتان حقيقيتان كُشفتا بالتجربة الفعلية** (لا افتراضاً):
1. مسار خاص (`_\__Feature__ApiService`) أضاف backslash زائداً بالخطأ فأنتج
   شيفرة لا تُصرَّف — اكتُشف بأوّل تشغيل تجريبي على شريحة `invoices`.
2. `invoices_list_screen.dart` لم يستورد `router.gr.dart`، فبقي
   `InvoicesFormRoute` غير معروفٍ رغم توليده فعلياً — درسٌ عام: **استيراد
   الودجة لا يكفي لاستدعاء الـRoute المولَّدة منها**، يلزم `router.gr.dart` صراحةً.

**✅ جُرِّب فعلياً** (2026-09-14) على نسخة معزولة كاملة: شريحة `invoices` من
الصفر، مع `flutter pub get` حقيقي و`build_runner` حقيقي — النتيجة: `dart
analyze` نظيف، **٢٨٨ اختباراً ناجحاً**، صفر مخالفة `check_structure` جديدة.

**عمداً خارج النطاق:**
- **لا اختبارات مولَّدة** — اختبار CRUD حقيقي يحتاج حقولاً حقيقية، لا `title`
  تجريبياً. المشروع يضيفها بعد تعديل الحقول.
- **يفترض عقد صفحة `{items, page, limit, total, total_pages}`** — نفس شكل
  `test/wire_contract_test.dart`. مشروعٌ بعقدٍ مختلف يعدّل
  `{feature}_remote_datasource.dart` وحده.

## 04 — سكربت تدقيق ذاتي للقالب (Template Doctor)

✅ **منجَز (2026-09-14)** — `scripts/audit_template.dart`.

**ما هو:** يُشغِّل آلياً فحوصاً أجريناها يدوياً بمحادثة التدقيق الكاملة
(2026-09-13): وصل كل موديول اختياري بإقلاعه · فجوة `offlineSync` الحرجة ·
مسارات مسجَّلة بلا نقطة تنقّل ظاهرة · ملفات `readme/` خارج جدول التزامن.
**استشاريٌّ لا حاجب** — يفشل (`exit(1)`) فقط عند الفحص الوحيد بصفر زيفٍ
إيجابيٍّ ممكن (الفجوة الحرجة)؛ الباقي مرشَّحاتٌ للمراجعة البشرية.

**لماذا الآن:** هذا التدقيق **يتكرر** — كل مشروع مستقبلي يستحق نفس الفحص قبل
الشحن، ولا معنى لإعادته بمحادثة كاملة كل مرة بينما جزء كبير منه آليٌّ صرف.

**ما نُفِّذ فعلياً — أربعة فحوص لا ثلاثة:**
1. **وصل الموديولات بإقلاعها** — نصّياً: هل ملفّ `*_plugin.dart`/`*_module.dart`
   مستورَدٌ بـ`modules_bootstrap.dart`؟ لا مطابقة اسم علَم بالاسم (استُبعدت
   عمداً: `sync`→`offlineSync` لا يتبع أي نمط تسميةٍ آلي، فمطابقةٌ بالاسم
   كانت ستُنتج زيفاً إيجابياً مضموناً على هذا الموديول بالذات).
2. **الفجوة الحرجة** — بحثٌ عن `extends/implements SyncFeatureContractBase`
   أو `@LazySingleton(as: SyncFeatureContractBase)` بكامل `lib/`، مقابل قيمة
   `AppFeatures.offlineSync`.
3. **مسارات بلا نقطة تنقّل** — اشتقاق اسم كل Route من `@RoutePage()` (إسقاط
   لاحقة `Screen`/`Page` + `Route`، أو الاسم الصريح)، ثم بحثٌ عن استخدامٍ آخر
   له بـ`lib/` غير `router.dart`.

## 09 — Deep Linking عام ✅ (2026-09-14)

**ما هو:** فتح شاشة محدَّدة من رابط خارجي (`https://…` أو مخطَّط تطبيق) —
وليس فقط قرار أول شاشة بالإقلاع البارد كما كان.

**لماذا الآن:** `deepLinkBuilder` بـ`app.dart` كان **يتجاهل** `PlatformDeepLink`
كلّياً ويُعيد `_startRoute` دائماً — إقلاعٌ عاديّ أو رابطٌ حقيقيّ، سيّان. فرابطُ
تفعيلٍ أو دعوةٍ وصل والتطبيقُ مغلقاً كان يُفتَح على وجهة `StartupResolver`
العادية لا وجهته، ورابطٌ يصل والتطبيقُ يعمل لم يكن له مسارٌ تشغيليّ أصلاً.

**ما بُني:**

- [`lib/routes/deep_link_resolver.dart`](../lib/routes/deep_link_resolver.dart)
  — دالّةٌ نقيّة `resolveDeepLink({initial, path, startRoute})` مستخرَجةٌ عمداً
  عن `app.dart` لتكون قابلة للاختبار المباشر بلا تركيب `App` كاملةً بتبعيّاتها.
  القرار: `initial && (path فارغ أو "/")` ← إقلاعٌ عاديّ (`DeepLink.single`،
  وجهة `StartupResolver` تحكم) — أي شيءٍ آخر ← `DeepLink.path(path)` يُحلّ عبر
  شجرة `router.dart` بحرّاسها (مثل `PermissionRouteGuard`).
- `lib/app.dart`: `deepLinkBuilder` يستدعي `resolveDeepLink` بدل الإعادة
  الثابتة لـ`_startRoute`.
- [`test/deep_link_resolver_test.dart`](../test/deep_link_resolver_test.dart)
  — ٥ اختبارات: إقلاعٌ عاديّ بلا مسار، إقلاعٌ عاديّ بمسار `"/"`، رابطٌ حقيقيّ
  عند الإقلاع، رابطٌ حقيقيّ والتطبيق يعمل، وحالة الحافة (`initial: false` +
  مسار فارغ — لا يُطبَّق استثناء الإقلاع العادي، فيُحلّ كما وصل).
- `readme/23_STARTUP_SPLASH.md` §٥ محدَّث بالسلوك الجديد وبسبب الاستخراج.

**تحقّق:** `dart analyze lib scripts` نظيف، `check_structure.dart` صفر
مخالفة جديدة، `flutter test` الكاملة (320 اختباراً) ناجحة — بما فيها
`test/router_contract_test.dart` القائم أصلاً (لا يفحص `deepLinkBuilder`
فيتعارض، يفحص تسجيل المسارات فقط).

**عمداً خارج النطاق:** تسجيلُ الرابط على مستوى نظام التشغيل — `intent-filter`
بأندرويد و`Associated Domains`/Universal Links بـiOS — **لم يُبنَ هنا**. هذا
البند يبني جانب Flutter وحده (تحويل `PlatformDeepLink` الوارد إلى
`PageRouteInfo` صحيح)؛ ربط مخطَّط أو نطاق فعليّ بالنظام يبقى قرار المشروع
المستهلك حسب الروابط التي يحتاجها فعلاً (لا حشو `AndroidManifest.xml` بمخطَّط
وهميّ لا يُستخدم). كذلك `path` صريح لكل `AutoRoute` — القالب اليوم بلا
features تطبيقية، فلا مسارات لها معنى تُضاف الآن؛ يُضاف حين يكتب المشروع أول
feature تحتاج رابطاً خارجياً.

  يُرسم هنا — هذا الملف عرضٌ فقط.
- `ErrorFallback` صنفٌ عامٌّ لا خاصّاً (رغم أن لا أحد يبنيه يدوياً بشاشة

- [`test/error_boundary_test.dart`](../test/error_boundary_test.dart) — ٣

## 12 — فحص «شاشة تطلب صلاحية لا تملكها» 🔵 (بُحث 2026-09-15 — مؤجَّل بقصد)

**ما هو:** موصوفٌ فعلاً بـ[`31_MODULE_PERMISSIONS.md`](31_MODULE_PERMISSIONS.md)
§«توصيات مستقبلية» رقم ٣ — ربط كل `Can(permission: ...)` بمفتاحه للتأكد أنه
مُعلَن فعلاً بالباك.

**لماذا الآن:** الفجوة الوحيدة غير الممسوكة اليوم بهذا الموديول — كل ما
سبقها (typo بالمفتاح، endpoint بلا حارس) له فاحص، وهذه لا.

**ولمّا بُحث فعلياً — لماذا لا فاحصٌ آليّ اليوم:** الحارسُ المركزيّ
(`PermissionRouteGuard`/`Can`) **يعمل بشكل صحيح دائماً** لأي مفتاح يُعطى إياه؛
العثرة الموصوفة (§العثرة ٦ بـ`31_MODULE_PERMISSIONS.md`) ليست خللاً به بل
نداءَ API **داخل** شاشة محروسة نسي أحدٌ تغليفه بمفتاحه الخاص. وفحصٌ آليٌّ لهذا
يحتاج ثلاثة أشياء لا واحد منها متاحٌ بالقالب اليوم:

1. **تطبيقاً حقيقياً بشاشاتٍ فعلية** — القالب مُنظَّفٌ من كل feature تطبيقية
   بقصد (راجع أعلى `CLAUDE.md`)، فلا نداء API واحد يُبنى عليه فحصٌ أصلاً.
2. **تتبّع استدعاء** يربط كل نداء بملف مصدره (Cubit ← UseCase ← Repository
   ← ApiService) — تحليلٌ ساكنٌ غير تافه.
3. **وصولاً لمستودع الباك** (`backend_template`) لمعرفة أيّ صلاحيةٍ يفرضها كل
   مسار — بياناتٌ لا يحملها `permissions.lock.json` (قائمة مفاتيح مسطَّحة
   بلا تعيين مسار↔صلاحية) ولا أي ملفّ آخر بهذا المستودع.

بناء فاحصٍ اليوم يعني إمّا صفر نتائج للأبد (لا شاشات) أو بيانات اختبارٍ
مصطنَعة لا تثبت شيئاً — وكلاهما يخالف معيار «تحقّقٌ حقيقيّ» المتَّبَع بهذا
الملف لكل بندٍ سابق.

**البديل المُنفَّذ بدلاً من الفاحص الآلي:** قائمة مراجعة يدويّة مُضافة إلى
[`31_MODULE_PERMISSIONS.md`](31_MODULE_PERMISSIONS.md) مباشرةً بعد «العثرة ٦»
(القسم الذي وصف الحادثة الحقيقية بقرطاس)، وسطرٌ تذكيريّ بـ«بطاقة الإنهاء» في
[`04_FIRST_FEATURE.md`](04_FIRST_FEATURE.md) يُشير إليها عند إغلاق أي شريحة
جديدة. هذا لا يُكتشف آلياً، لكنه يضع السؤال أمام أول من يبني شاشة محروسة —
وهي اللحظة التي وقعت فيها العثرة الحقيقية أصلاً.

**طريقة الدمج المقترحة (إن ظهرت حاجة مشروعٍ حقيقي لاحقاً):** يحتاج تفكيراً
معمارياً (كيف يُربط استدعاء `Can` بملف مصدره لإنتاج قائمة) + مستودع الباك
مرئياً لأداة الفحص — أُجِّل عمداً للسببين معاً.

**نقاش وتوسّع أثناء التطبيق:** طُرح سؤالٌ وجيه أثناء البحث: أليس هذا مركزياً
بالفعل عبر الموديول (تحذيرٌ ومنعٌ تلقائيان)؟ والجواب: نعم، لكن فقط لما تُخبره
الشاشةُ به. الحارس المركزي يحرس **الدخول** بمفتاحٍ واحد تعلنه أنت؛ ولا يعرف
تلقائياً أن عنصراً داخلياً (منتقياً، فلتراً) يستدعي مفتاحاً **آخر** لم يُصرَّح
به — تلك معرفةٌ لا يملكها الفرونت أصلاً بلا الرجوع لعقد الباك لكل نداء.

## 15 — ربط `scaffold_feature.dart` بسلسلة المزامنة والصلاحية تلقائياً ✅ (2026-09-15)

**ما هو:** اقتراحٌ نشأ أثناء نقاشٍ عن أدواتٍ توفّر جهداً عند بدء أي تطبيق —
`scaffold_feature.dart` كان يولّد الطبقات الأساسية فقط (CRUD صرف)، ويترك ربط
الشريحة الجديدة بموديولَي المزامنة/الصلاحية (إن كانا مُشعَلين) عملاً يدوياً
بالكامل — عملٌ يتكرر مع **كل** شريحة تُبنى، لا مرّةً واحدة.

**لماذا الآن:** التوثيق الفعلي لتكلفة الربط اليدوي موجودٌ ومقيسٌ فعلاً
(`lib/modules/sync/PLAN.md` §P2.7: ٣٩١ سطراً و٤ ملفات لكل كيان)، وفخّ التخمين
الصامت لاسم مفتاح صلاحية موثَّقٌ بـ«العثرة ٦» بـ`31_MODULE_PERMISSIONS.md`.

**ما بُني:**

- السكربت يقرأ `AppFeatures.offlineSync`/`AppFeatures.accessControl` مباشرةً
  من `app_features.dart` — **بلا سؤالٍ تفاعلي**؛ مشروعٌ لم يُشعلهما لا يرى
  فرقاً ولا ملفاً إضافياً واحداً (صفر أثر، نفس عقد كل قدرة اختيارية بالقالب).
- `offlineSync == true` ⇒ أربعة ملفات `data/sync/` جديدة (عقد · منفّذ دفعٍ
  يعيد استعمال `HandleBodyResponse` نفسه لا نسخةً موازية · ديكور تسجيل ·
  `SyncAware<Feature>Repository`). **الكتابة توليدٌ آمنٌ كامل** (تُصفّ فعلاً
  بلا اتصال، عبر `SyncWriteGateway` بحقول `SyncWriteCommand` الصحيحة).
  **والقراءة عبورٌ شبكي عمداً** — قراءةٌ محلّية-أولاً حقيقية تحتاج مؤشّر
  ترقيمٍ يخصّ الشاشة، ولا مثال حيٍّ بالقالب اليوم يُقتدى به بثقة (`notes/`
  المرجعي حُذف)، وتوليد ٢٢٧ سطراً بلا تحقّقٍ حقيقي أخطر من عدم توليدها —
  نفس الدرس الذي وثَّقه `PLAN.md` عن توثيقٍ ادّعى اكتمالاً لم يُختبَر قطّ.
- `accessControl == true` ⇒ زرّ الإضافة يُغلَّف بـ`Can(permission:
  PermKeys.<feature>Create, ...)`. **يكسر البناء عمداً** حتى يُعلن الباك
  المفتاح فعلياً ويُعاد `gen_permission_keys.dart` — البديل (تخمين اسم
  المفتاح صامتاً) هو بالضبط الخطأ الذي بُني `PermKeys` أصلاً ليمنعه.
- خطوةُ `dart format` على مجلّد الشريحة أُضيفت للسكربت (لم تكن موجودة) —
  لازمةٌ لأن استبدال الرمز الشرطي (FAB عادي/مُغلَّف) ينتج مسافاتٍ غير مهذَّبة.
- رسالة إغلاقٍ مخصَّصة حين يفشل التحليل بسبب `PermKeys` تحديداً — توضّح أن
