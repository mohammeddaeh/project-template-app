# مسار الخطأ — العقد الكامل عبر النصفين

> **المرجع الواحد** لما يحدث بين «السيرفر رفض» و«المستخدم قرأ جملة يفهمها».
> يشمل `backend_template` و`app_template` معاً، لأن نصف القواعد هنا **لا تُرى إلا بالطرفين**.
>
> **يُحدَّث هذا الملف** عند تغيير: ترتيب الـinterceptors · `Failure` أو `FailureUiMapper` · `error-handler.ts` أو `MESSAGES` · ترتيب middleware بـ`app.ts` · أي حدث بـ`AuthEventBus`.

---

## المسار كاملاً

```
                      ┌─────────────── backend_template ───────────────┐

  requestContext          ← req.lang من Accept-language (قبل express.json)
       ↓
  express.json()          ← يرمي عند جسم تالف/كبير → asBodyParserError → 400/413
       ↓
  auth → route → validate(zod) → controller → service
       ↓ throw ApiError(message, …, messageKey)
  errorHandler            ← المكان **الوحيد** الذي يُبنى فيه جسم خطأ
       ↓ resolveErrorMessage(fallback, req.lang, messageKey)
  { status:false, message, code, errors?, data? }

                      └───────────────────────┬───────────────────────┘
                                              ▼
                      ┌─────────────── app_template ──────────────────┐

  Dio interceptors        ← الترتيب سلوك، راجع §الترتيب
       ↓ DioException
  FailureMapperRegistry   ← Exception → Failure (بيانات خام، بلا ترجمة)
       ↓
  BaseRepository.handle() ← الحدّ الوحيد؛ لا try/catch يدوي بأي repository
       ↓ Either<Failure, T>
  UseCase → Cubit
       ↓
  FailureUiMapper.toAction(failure)   ← المكان **الوحيد** الذي تُستدعى فيه .tr()
       ↓
  ShowError | NavigateToLogin | Silent
       ↓
  emit(State.error) → الشاشة

                      └───────────────────────────────────────────────┘
```

**كل «المكان الوحيد» أعلاه حرفية.** خرقُها لا يُنتج خطأ ترجمة — يُنتج شاشةً تعرض نصّاً إنجليزياً لقارئ عربي، أو رسالة عامّة بدل سبب معروف، ولا يفشل شيء.

---

## 1) الترتيب — أربع قواعد سلوكية

الترتيب ليس تنظيماً. نقلُ سطر يغيّر ما يراه المستخدم، ولا يفشل أي فحص.

| # | القاعدة | ما حدث فعلاً حين خُولفت |
|---|---|---|
| **1** | **`RequestCacheInterceptor` قبل `InternetCheckerInterceptor`** | كان بعده. Dio ينفّذ `onRequest` بترتيب التسجيل، فالحارس يرفض الطلب **قبل** بلوغ الكاش. النتيجة: الكاش يعمى بالحالة الوحيدة التي وُجد لأجلها — جهاز بلا شبكة والجواب على قرصه |
| **2** | **`AuthInterceptor` قبل `TokenRefreshInterceptor`** | التجديد يُعيد إرسال طلبٍ بلا `Authorization` فيُرفض ثانيةً — حلقة 401 لا تنتهي |
| **3** | **`requestContext` قبل `express.json()`** | كان بعده. الـparser أوّل ما يرمي، و`errorHandler` يترجم بـ`req.lang` — وهي `undefined` على المسار الوحيد الذي احتاجها |
| **4** | **`notFound` ثم `errorHandler` آخر شيء** | مسار غير مطابق يعبر إلى معالج Express الافتراضي فيردّ HTML بدل مغلّف JSON، ويصل الفرونت `ParseFailure` بدل 404 |

> **المصدر الوحيد للترتيب**: `core/di/injection_module.dart` (فرونت) و`src/app.ts` (باك). الرسوم بالوثائق مرايا لهما — وقد كان رسم `NETWORK.md` يصف ترتيباً **لم يُطبَّق قط**، فأي قارئ استنتج منه سلوكاً استنتج خطأً.

## 2) اللغة — رأس واحد يمرّ بكل طلب

```dart
// auth_interceptor.dart — خارج if (token != null) عمداً
options.headers['Accept-language'] = _localeProvider.languageCode;
```

كان داخل `if (token != null)`. فكل رفض يقابله المستخدم **قبل امتلاك جلسة** وصل بلغة السيرفر الافتراضية (`ar`):
كلمة مرور خاطئة · حساب بانتظار الموافقة · مرفوض · موقوف · معطَّل · تجاوز محاولات · بريد مكرَّر بالتسجيل · مسار استعادة كلمة المرور كاملاً.

**وهي بالضبط الرسائل التي فُصلت إلى أنواع مسمّاة** بـ`failure.dart` لتقول للمستخدم ماذا يفعل تالياً — فوصلت بلغة قد لا يقرؤها، على الشاشة الوحيدة التي لا يملك فيها أي دليل آخر.

| القاعدة | التحقق |
|---|---|
| الرأس يُرسَل **دائماً**، بتوكن أو بدونه | `request-context.ts` يقرؤه بكل طلب ويردّ `ar` افتراضاً |
| الرفض المرئي للمستخدم يحمل `messageKey` | `npm run check:messages` — يفشل البناء، لا يُحذّر |
| العميل يتفرّع على `data.message_key` **لا على نصّ الرسالة** | النصّ نثرٌ مترجَم يتغيّر بلغة كل طلب |

## 3) ما يُصنَّف خطأً وما لا يُصنَّف

### الباك — ثلاثة أنواع لا تُدمج

| الحالة | الردّ | لماذا لا 500 |
|---|---|---|
| جسم تالف / أكبر من الحدّ | **400 / 413** | خطأ العميل، وقابل للإصلاح بإعادة الإرسال. كان 500، والفرونت يترجم 500 إلى `ServerFailure` بـ`canRetry: false` — **طريق مسدود على أكثر الأعطال قابليةً للتعافي**. رفعُ ملف انقطع على شبكة متذبذبة يقع هنا |
| تبعية غير متاحة (قاعدة بيانات، مقبس) | **503 + Retry-After** | 500 تقول «معطوب»، فيرى المستخدم نهايةً مسدودة بينما ثوانٍ من الانتظار كانت تكفي |
| عطبٌ حقيقي بالكود | **500** | وهذا وحده |

### الفرونت — 500 و503 ليسا نفس الشيء

| Failure | `canRetry` | السبب |
|---|---|---|
| `ServerFailure` (500/501/505) | ❌ | نفس الطلب بعد ثانية يُنتج نفس الـ500. زر إعادة لا يعمل أبداً أسوأ من غيابه |
| `ServiceUnavailableFailure` (502/503/504) | ✅ | «مشغول الآن، حاول قريباً» صادقة هنا وكاذبة فوق |
| `ServerUnreachableFailure` | ✅ | الجهاز متصل ولا أحد يجيب — **الذنب ليس ذنب اتصال المستخدم، والرسالة يجب ألّا تتّهمه** فيذهب يعيد تشغيل الراوتر |
| `RateLimitFailure` (429) | ❌ | إعادة المحاولة فوراً هي بالضبط ما أنتج الـ429 |

**و`RetryInterceptor` يحترم `Retry-After`**: تجاهله يحوّل ضغطاً إلى انقطاع — السيرفر يقول «بعد ٦٠ ثانية» فيعود العميل بعد واحدة ثم اثنتين ثم أربع، وكل العملاء معاً هي الـstampede التي وُجد الرأس ليمنعها. وطلبٌ أطول من `maxHonouredRetryAfter` **يُظهَر فوراً** بدل حجزه خلف مؤشّر يبدو معلَّقاً.

## 4) 401 و403 — الفرق الذي يُفقد المستخدم عمله

```
401 → UnauthorizedFailure → NavigateToLogin   (لا نعرف من أنت)
403 → ForbiddenFailure    → ShowError         (نعرفك تماماً، والجواب لا)
```

دمجُهما يُخرج المستخدم من التطبيق بسبب صلاحية واحدة ناقصة، **وسط مهمّة**. وقع فعلاً بمشروع قرطاس: معالج `AuthEventBus` كان ينقل لشاشة الدخول عند أي حدث، فأول 403 سجّل الخروج. الحارس الآن `switch` شامل بـ`app.dart` — حدثٌ جديد يصير **خطأ ترجمة** لا خروجاً صامتاً.

### وكل خروج قسري **يقول سببه**

| الحدث | ما يُعرَض |
|---|---|
| `sessionExpired` | `sessionExpiredMessage` — «انتهت جلستك» |
| `sessionRevoked` | `sessionRevoked` — «تم تسجيل خروجك من جهاز آخر» |
| `permissionsStale` | **لا شيء** — `AbilitiesStore` يُعيد قراءة `/authz/me` والمستخدم يبقى مكانه |

كان الأولان ينقلان بلا كلمة واحدة. مستخدمٌ وسط مهمّة يُلقى على شاشة الدخول بلا تفسير **يقرأها انهياراً وفقداناً لعمله** — والمفتاحان كانا موجودَين بلا مستدعٍ. والثاني تحديداً هو الطريقة الوحيدة ليلاحظ أحدٌ دخولاً لم يقم به.

## 5) قواعد لا تُخالَف

| القاعدة | لماذا |
|---|---|
| **`catch (_) {}` ممنوع** — كل مسار احتياطي يسجّل | `RequestCacheInterceptor` كتب مدخلات **لم يستطع قراءتها قط** طوال عمره: قراءة بلا `await`، فتحويل يرمي، فـ`catch` صامت يبتلع. سلوكه المُلاحَظ = كاش بارد أبداً. `dart analyze` نظيف، كل الفحوص خضراء، **ولا عَرَض يُبحث عنه**. العلّة لم تكن نسيان `await` — بل الـcatch الذي جعل النسيان غير قابل للملاحظة |
| **`StorageService.clear()` لا تُستدعى لمسح جزء** | `invalidateAll()` كانت تستدعيها فتمحو الثيم واللغة والخط ولقطة المستخدم — بدالّة اسمها «امسح كاش HTTP» وتوثيقها يَعِد بذلك. من يملك بادئة يمسح مفاتيحه عبر `keys()` + `delete()` |
| **الترجمة بـ`FailureUiMapper` وحده** | `Failure` بيانات خام. `.tr()` بطبقة الـdata تعني رسالةً بلغة اللحظة التي وقع فيها الخطأ لا لحظة قراءته |
| **الـrepositories لا تكتب try/catch** | `handle()` هو الحدّ. استثناء يُلتقط يدوياً يفوّت `FailureMapperRegistry` فيصل الشاشةَ `UnknownFailure` بدل نوع معروف |
| **الباك لا يبني جسم خطأ يدوياً** | `res.status(x).json(...)` داخل controller يتخطّى الترجمة والتسجيل ومغلّف `data` معاً |
| **رسالة الخطأ ليست عقداً** — العقد `data.message_key` | النصّ يتغيّر بأي إعادة صياغة، والفرع المبني عليه ينكسر باللغة التي لم يجرّبها أحد |

## 6) أخطاء المستخدم — المتوقَّعة تُمنع لا تُبلَّغ

| التوقّع | المعالجة بالقالب |
|---|---|
| ضغط مزدوج على «إرسال» | `_isLoading` guard + `isEnabled: !_isLoading` — راجع §FORMS-GUIDE |
| إرسال نموذج ناقص | `_submitted` يفعّل `autovalidateMode` بعد أول محاولة — لا قبلها، فالحقل الفارغ لم يُخطئ بعد |
| حذف بالخطأ | `AppConfirmDialog.show(..., isDestructive: true)` **إلزامي قبل أي حذف** |
| مغادرة شاشة قبل وصول ردّها | `SafeCubit` — غير مشروط. الانهيار الحقيقي `Bad state: Cannot emit new states after calling close` يصل نسخة الإصدار |
| قائمة فارغة تُقرأ «لا يوجد شيء» وهي مفلترة | شرائح الفلترة **تشمل نصّ البحث نفسه** — مفلترة فارغة ومنظَّمة فارغة تتطابقان بصرياً |
| بريد غير مسجَّل بـ«نسيت كلمة المرور» | الجواب **نفسه** للمسجَّل وغيره — وإلا صار الـendpoint عرَّاف عضوية |
| كلمة مرور حالية خاطئة | **422 لا 401** — الـ401 يردّ عليها المعالج المركزي بتسجيل خروج، فخطأٌ بحقل واحد يطرد المستخدم |
| رفع ملف أكبر من الحدّ | 413 برسالة مترجَمة — لا 500 |

## 8) عند إضافة نوع خطأ جديد

```
1. backend:  ApiError subclass أو BusinessError + messageKey بـ core/i18n/messages.ts
2. backend:  npm run check:messages   ← يفشل حتى يُسجَّل المفتاح
3. frontend: final class XFailure extends Failure  (بيانات خام فقط)
4. frontend: DioFailureMapper / FailureMapperRegistry ← متى يُبنى
5. frontend: FailureUiMapper ← switch شامل، فالمُصرِّف يفشل حتى تُغطّيه
6. frontend: مفاتيح ar.json + en.json ثم أمرَي easy_localization
7. المرآة:   صف بسيناريو #07 (TestFailureDemoScreen) — جدول المرآة بـCLAUDE.md
8. هذا الملف: صف بالجدول المناسب أعلاه
```

الخطوة 5 هي الحارس: `Failure` مُعلَّمة `sealed`، فنوعٌ جديد بلا معالجة **لا يُصرَّف**. لا شيء يُنسى صامتاً.
